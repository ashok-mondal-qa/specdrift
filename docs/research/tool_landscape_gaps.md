# Test-automation tool landscape and gaps (state as of 12 Oct 2026)

Method note: star counts, last-push dates, licences and archived flags were read from the GitHub REST API on 2026-10-12 (via `gh api repos/<owner>/<repo>`), and niche-repo discovery used `gh search repos` sorted by stars on the same day. "Last push" is the repo's `pushed_at`, not necessarily a release. Commercial pricing mostly came from third-party pages and is flagged where it was not confirmed on the vendor's own site. GitHub search was rate-limited part-way through, so three queries ("test analytics junit", "allure history github pages", "test observability open source") returned nothing; absence of results for those is not evidence of absence.

## Key question 1: In which areas is there a clear, verifiable gap a single developer could fill in 2-3 months part-time?

### Takeaway
The best-evidenced gaps are (a) change-based test selection for Playwright end-to-end suites that maps application-code changes to tests (nothing credible exists in open source; Playwright's own flag only looks at changed test files), (b) deterministic Selenium-Java to Playwright-TypeScript migration (one 3-star tool where the Java path is an "experimental MVP", plus a crowd of 0-1 star LLM wrappers), and (c) OpenAPI drift/coverage checking for the mocks and live traffic in Playwright UI tests (the obvious prior tools are archived or stale). Flaky-test dashboards for Playwright looked like a gap a year ago but are now crowded with small self-hosted projects.

### Cited Findings

#### Area 1 - Flaky-test detection, scoring, quarantine

Open source / source-available:
- Playwright itself (97,513 stars, v1.64.0 released 2026-10-07, Apache-2.0) has only per-run flaky handling: `--retries`, `--fail-on-flaky-tests` ("Fail if any test is flagged as flaky"), `--last-failed`. No cross-run history. — [Playwright CLI docs](https://playwright.dev/docs/test-cli); [repo](https://github.com/microsoft/playwright)
- PiwiTests/platform: self-hosted Playwright dashboard with run history, failure clustering by error fingerprint, composite flaky score with root-cause class and wasted CI minutes, locator healing, MCP server. 36 stars, 4 forks, created 2025-12-07, last push 2026-10-11, 4,081 commits. Licence is FSL-1.1-MIT ("fair source", converts to MIT after two years), not OSI open source. Explicitly "deliberately Playwright-only" and points users with JUnit/pytest/Cypress results to ReportPortal or Allure. Docker one-liner, SQLite or PostgreSQL. — [PiwiTests/platform](https://github.com/PiwiTests/platform)
- CyborgTests/playwright-reports-server: MIT, 218 stars, 22 forks, created 2024-03-30, last push 2026-09-21. Stores and merges shard reports; analytics dashboards with pass-rate trends, slow tests, failure clusters; "score test stability"; optional quarantine via reporter-side skip; SQLite + local/S3/Azure storage. Playwright only. — [CyborgTests/playwright-reports-server](https://github.com/CyborgTests/playwright-reports-server)
- kinora-dev/kinora: self-hosted dashboard for Playwright/Vitest/Storybook across projects and over time; 35 stars, last push 2026-10-12, non-standard licence. — [kinora-dev/kinora](https://github.com/kinora-dev/kinora)
- qa-gary-parker/playwright-smart-reporter: MIT, 49 stars, last push 2026-10-08; HTML reporter with a local history file and flakiness tracking across runs. — [repo](https://github.com/qa-gary-parker/playwright-smart-reporter)
- ctrf-io/github-test-reporter: MIT, 378 stars, last push 2026-10-11. Has `flaky-report`, `flaky-rate-report`, `fail-rate-report`, `previous-results-report`, `insights-report`. History is reconstructed by fetching CTRF artifacts from previous GitHub workflow runs through the GitHub API (defaults: check up to 400 workflow runs, fetch up to 100 previous). It is a GitHub Action; the README does not describe use outside Actions. Accepts CTRF or JUnit. — [ctrf-io/github-test-reporter](https://github.com/ctrf-io/github-test-reporter)
- Allure Report: flaky mark requires a failure within the latest 5 launches, a pass since, and a fail/broken in the latest launch; depends on history being enabled and carried between runs. allure2 5,556 stars (last push 2026-10-01), allure3 425 stars (v3.20.1, 2026-10-06), both Apache-2.0. — [Allure test stability docs](https://allurereport.org/docs/test-stability/); [allure2](https://github.com/allure-framework/allure2); [allure3](https://github.com/allure-framework/allure3)

#### Area 3 - Test impact analysis / change-based selection

- Playwright `--only-changed [ref]`: "Only run test files that have been changed between 'HEAD' and 'ref'... Only supports Git." There is also `--test-list <file>` to run an externally supplied list of tests, which is a ready-made integration point for an external selector. — [Playwright CLI docs](https://playwright.dev/docs/test-cli)
- Datadog Test Impact Analysis: per-test code coverage compared with changed files; setup guides for .NET, Java, JavaScript, Swift, Python, Ruby, Go. Documented blind spots: library dependencies, compiler options, external services, data files in data-driven tests. Only the 100 most recent commits analysed; commits touching more than 5,000 files are not analysed. The overview page does not mention Playwright. — [Datadog TIA docs](https://docs.datadoghq.com/tests/test_impact_analysis/)
- Datadog Java TIA supports JUnit 4.10+/5.3+, TestNG 6.4+, Spock, Cucumber, Karate, Scalatest via dd-java-agent 1.27.0+. — [Datadog TIA Java setup](https://docs.datadoghq.com/tests/test_impact_analysis/setup/java)
- CloudBees Smart Tests (formerly Launchable): predictive test selection now described as LLM-based similarity between changed files and test files; SaaS only; CLI is Python 3 (cloudbees-oss/smart-tests-cli, 27 stars, Apache-2.0, last push 2026-10-09); vendor claims up to 80% time cut; no public price found. — [Predictive Test Selection docs](https://docs.cloudbees.com/docs/cloudbees-smart-tests/latest/features/predictive-test-selection); [smart-tests-cli](https://github.com/cloudbees-oss/smart-tests-cli)

### Inferences
- Ranked by "verified emptiness x feasibility":
  1. Playwright E2E test selection from application-code changes. Evidence of emptiness is strong (0-star repos only; official flag is test-file based; Datadog and CloudBees are paid SaaS and Datadog's docs do not mention Playwright). `--test-list` gives a clean hand-off. A scoped design (record which routes/API endpoints/source files each test touches via coverage or network capture, then emit a test list for a diff) looks buildable solo, but correctness (never skipping a test that would have failed) is the hard part and needs an honest safety story.
  2. OpenAPI drift and coverage for Playwright UI tests: validate `page.route` mocks, HAR files and live responses against the backend's OpenAPI spec and report which endpoints the UI suite exercises. Optic and Dredd being archived and the 0-star search results suggest a real opening. This is the most tractable in 2-3 months because it is mostly a Playwright fixture plus an existing validator library.
  3. Selenium-Java to Playwright-TS migration with a deterministic core (Java AST, mapping profiles, TODO report). The gap is verified, but LLM coding agents already do ad-hoc conversion, so the differentiator would have to be auditability and whole-suite handling (page objects, waits, TestNG to Playwright fixtures), and the long tail is large.
  4. Appium reporting/flake tooling: the stale plugins are evidence of a gap, but development needs devices/emulators and the audience is smaller.
- A cross-framework, lightweight flaky scorer that ingests CTRF/JUnit from Playwright, TestNG and Appium runs is still a defensible niche (Piwi explicitly declines non-Playwright; CTRF's reporter is tied to GitHub Actions artifacts), but it is adjacent to a crowded field and would be judged against it.

### Gaps
- npm and Maven Central were not searched, so a Playwright OpenAPI-validation fixture or a TIA package may exist there without a notable GitHub repo. Check npm for "playwright openapi" and "playwright impact" before committing.
- Whether rwx Captain's flaky detection and quarantine work without an RWX cloud account was not established; the README does not say.
- ReportPortal's self-hosting footprint (services, RAM) could not be confirmed: the system-requirements docs URL returned a 404. The common claim that it is "heavy" is therefore unverified here.
- Not inspected at source: Gradle Develocity, Microsoft/Azure DevOps TIA, Bazel, Nx affected behaviour, Testmo, Tesults, LangSmith, GitHub-native flaky features, Detox internals, Pact/Specmatic/Microcks feature gaps. No weaknesses are claimed for them.
- Whether promptfoo, DeepEval or others already offer a first-class browser/UI-level provider for testing chat UIs was not checked; the "no UI-level LLM testing tool" impression rests only on two GitHub searches.
- Whether any tool offers baseline/"fail only on new violations" history for axe results was not checked.
- Exact behaviour of `--only-changed` regarding files imported by tests was not confirmed beyond the one-line CLI description.

## Key question 2: In which areas would a new project be redundant?

### Takeaway
LLM evaluation frameworks, AI browser agents, visual regression, accessibility scanning, generic contract testing, and (as of 2026) self-hosted Playwright run dashboards with flaky scoring are all well served; a new solo project there would be repackaging.

### Cited Findings

## Key question 3: Are there emerging standards worth building on?

### Takeaway
CTRF is the most practical interchange format to build on today (small but very actively maintained, with reporters for most runners and a JUnit converter); JUnit XML remains the universal fallback; OpenTelemetry has `test.*` attributes but they are still "Development" stability with almost no adoption in test tooling; Playwright's `--test-list` and MCP are useful integration surfaces rather than standards.

### Cited Findings
- CTRF: spec repo 100 stars, MIT, pushed 2026-10-10; reporters for Playwright (105 stars), Jest, Cypress, Mocha, WebdriverIO, Go, .NET, Newman, plus `junit-to-ctrf`; a community RSpec formatter exists. — [ctrf-io/ctrf](https://github.com/ctrf-io/ctrf); [playwright-ctrf-json-reporter](https://github.com/ctrf-io/playwright-ctrf-json-reporter); [junit-to-ctrf](https://github.com/ctrf-io/junit-to-ctrf); [rspec-ctrf](https://github.com/dusc-dev/rspec-ctrf)
- CTRF's own GitHub reporter accepts CTRF or JUnit and says CTRF works best. — [github-test-reporter](https://github.com/ctrf-io/github-test-reporter)
- OpenTelemetry semantic conventions define `test.suite.name`, `test.case.name`, `test.case.result.status` (pass/fail) and `test.suite.run.status`, all in Development stability; there is also a separate `cicd` group. semantic-conventions repo: 667 stars, pushed 2026-10-12. — [OTel test attribute registry](https://opentelemetry.io/docs/specs/semconv/registry/attributes/test); [semantic-conventions](https://github.com/open-telemetry/semantic-conventions)
- OTel adoption in test tooling is thin: endformdev/playwright-opentelemetry 27 stars (2026-09); aergonaut/playwright-opentelemetry-reporter 15 stars; mdelapenya/junit2otlp 15 stars and uses its own `tests.suite.*` metric names rather than the semconv attributes; Tracetest 1,330 stars with last push 2025-06-03. — [endformdev/playwright-opentelemetry](https://github.com/endformdev/playwright-opentelemetry); [playwright-opentelemetry-reporter](https://github.com/aergonaut/playwright-opentelemetry-reporter); [junit2otlp](https://github.com/mdelapenya/junit2otlp); [tracetest](https://github.com/kubeshop/tracetest)
- Playwright exposes `--test-list <file>` / `--test-list-invert <file>` and `--last-failed-file`, letting external tools decide what runs or is skipped without patching the runner. — [Playwright CLI docs](https://playwright.dev/docs/test-cli)
- MCP is already the default surface for agent-driven testing: playwright-mcp 38,038 stars; appium-mcp 498; mobile-mcp 9,026; Piwi ships an MCP server. — [playwright-mcp](https://github.com/microsoft/playwright-mcp); [appium-mcp](https://github.com/appium/appium-mcp); [Piwi](https://github.com/PiwiTests/platform)

### Inferences
- Reading CTRF (and JUnit XML via the converter) as input gives a new tool Playwright, TestNG/JUnit and Appium-runner coverage at once, which is the cheapest route to "cross-framework" differentiation.
- Emitting OTel spans is a reasonable optional output but not a foundation: the attributes may still change and there is no ecosystem of consumers yet.
- `--test-list` makes both test selection (area 3) and quarantine (skip list) implementable as external CLIs, which fits a solo scope.

### Gaps
- CTRF's adoption outside its own organisation (who consumes it besides ctrf-io tools) was not measured; npm download counts were not checked.
- Playwright blob-report format stability and whether it is documented for third-party consumption was not checked.
- No source was found for a JUnit XML successor being standardised anywhere else.
